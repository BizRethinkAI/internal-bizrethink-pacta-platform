## Behavior and wiring

- **A-12:** `document-permissions.ts:getRecipientSuggestionWhere` verifies selected-team membership before either suggestion query. The recipient history retains owner, permitted-role and team-email access within that team; the fallback team-directory query also retains requester membership. An absent/foreign team or failed membership read cannot fall through to a directory query. Existing filtering, five-result limit, deduplication and one member suggestion are preserved.
- **A-13:** `getEnvelopeFileWhereInput` first reads only the envelope's team binding under any verified presign scope. It applies the existing metadata reader's owner/role/team-email policy and fixes that role to its actual team. Every ordinary PDF data query receives the complete predicate; a concurrently moved document cannot borrow the former team's role. Organisation-shared templates retain access where a current team in the same organisation grants their visibility; private templates/documents cannot use this exception. For human sessions, file URLs do not contain a selected team, so any qualifying current team in that organisation suffices. API and presign credentials cannot borrow that sibling-team role: they retain their issuing team’s current role, alongside independent AND restrictions for the verified team/resource scope.
- The three file handlers cover previews, original/signed/pending downloads and initial/current item PDFs. The membership-only `checkEnvelopeFileAccess` helper is removed. All `/api/files/envelope/*` responses use private/no-store, including errors and conditional responses, so a stored browser/proxy response cannot bypass later access checks. Recipient/QR/direct-link routes keep their separate merged policy and signing-deadline decision.
- **A-23:** legacy document deletion uses the same NOT_FOUND/`Document not found` outcome for absent and unauthorized objects. Its existing initial server-side lookup remains necessary for recipient self-hide; no unauthorized content is returned. The envelope delete wrapper now authorizes its type-dispatch lookup, permits only document recipients to take the self-hide exception, retains API team scope outside all branches and normalizes expected absence/access errors. Unexpected database/service failures remain failures. Ordinary PDF paths return identical 404/`Not found` responses for absent/foreign/hidden envelope/item identifiers. No timing-equivalence or repository-wide error audit is claimed.
- **A-24:** owned `folder-permissions.ts` replaces the two folder mutation implementations through thin upstream exports. Source/destination rows are locked and visibility is checked before an update. Deletion locks the selected parent before discovering/locking its children, repeating per level, and refuses any inaccessible, cross-team, wrong-kind or cyclic descendant. The existing cascade remains: folders disappear, envelopes and PDF data survive with `folderId = null`.
- Folder transactions explicitly use Read Committed so a waited-for row and newly committed children are checked. FOR UPDATE prevents changes to locked rows and conflicts with the parent FK's key-share check when another writer inserts/moves a child. A recursive snapshot followed by locking would not provide that property. Locks are only on affected rows, with sorted acquisition within each group. PostgreSQL may abort overlapping/deadlocked operations; they fail closed and can be retried, with no internal automatic retry. Existing Prisma transaction timeouts remain. Concurrency coverage uses actual PostgreSQL waits, not fixed sleeps or a lock-simulating mock. Reference: [PostgreSQL row locking](https://www.postgresql.org/docs/18/explicit-locking.html#LOCKING-ROWS), read 2026-09-12.
